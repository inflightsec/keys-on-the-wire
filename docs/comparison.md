# Why this and not the alternatives

`keys-on-the-wire` is for the single-host case where you already run Bitwarden Secrets Manager, prefer not to stand up a second vault, and want the credential bytes to literally never enter the agent's process.

Other tools in this space:

- **[HashiCorp Vault Agent](https://developer.hashicorp.com/vault/docs/agent-and-proxy/agent) / [Infisical Agent](https://infisical.com)**: render templates with real secrets to files the agent reads. Excellent at limiting what a leaked vault token exposes, but the per-API secrets still land in the agent's filesystem (and from there easily in its memory). No isolation at the agent boundary for the per-API secrets themselves.

- **[Doppler](https://www.doppler.com) / [`op run`](https://developer.1password.com/docs/cli/reference/commands/run/) / [`aws-vault exec`](https://github.com/99designs/aws-vault)**: inject secrets into the agent's process environment at start time. Same exposure: real secret bytes live in the agent's address space for the duration of the run.

- **[`superfly/tokenizer`](https://github.com/superfly/tokenizer)** - same substitution-on-the-wire idea, different deployment story. Supports header injection plus HMAC, SigV4, and JWT processors. Does not terminate TLS for clients (it speaks plain HTTP to the proxy and assumes a separate secure transport like a VPN protects that hop). Apache-2.0. Useful primitive, not a drop-in for the local-host case where you don't have that secure-transport assumption.

- **[Envoy `credential_injector` filter](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/credential_injector_filter)**: the general-purpose L7 proxy does the same wire-injection via a built-in HTTP filter, credentials from an SDS source or an OAuth2 client-credentials grant, injected as Basic/Bearer into the `Authorization` header. But it is built for mesh/sidecar **workload** auth: it authenticates the one workload behind the proxy, not per-destination agent secrets, and injects only into `Authorization` (no body/query, no per-binding host+method+path scope, no just-in-time vault sourcing, no honeytokens). kow is the focused, single-host, BWS-sourced version of the same primitive for the untrusted-agent threat model.

- **[Kloak](https://www.getkloak.com)**: eBPF substitution at `SSL_write` (and similar TLS write functions) for any OpenSSL/BoringSSL/Go-`crypto/tls` runtime in a Pod. Kubernetes-only, mutating admission webhook, DaemonSet, Pod-label opt-in, no documented standalone single-host install path, and AGPL-3.0. kow applies the same substitution-on-the-wire idea to any process on any host, not just Pods in a cluster.

- **[Deno Claw Patrol](https://github.com/denoland/clawpatrol)**: Deno's open-source agent firewall (Go, MIT). Same substitution-on-the-wire idea, delivered as a network gateway: the agent's traffic is captured at the routing layer via a WireGuard/Tailscale exit node rather than an opt-in `HTTP_PROXY`, so it gates any protocol - HTTP, Postgres, ClickHouse, Kubernetes, SSH - and adds an HCL/CEL policy engine with allow/deny and human/LLM approval chains. The trade-off is the one kow exists to avoid: secrets live in its *own* store (dashboard or `CLAWPATROL_SECRET__` env vars), so you copy them out of your existing vault instead of sourcing from it, and injection is mostly static (OAuth captured at setup; one EKS STS-presign case). It is the heavier choice for the "I don't control the host's egress, and I need multi-protocol policy" case; kow stays the thin layer that sources from BWS just-in-time and never introduces a second vault.

- **[iron-proxy](https://github.com/ironsh/iron-proxy)** (Apache-2.0, Go): the closest direct comparison. A standalone TLS-terminating, default-deny egress firewall that swaps proxy tokens for real credentials on the way out, shipped as a single Linux/macOS binary, and wired in as the sandbox egress layer of [Nous Research's Hermes Agent](https://github.com/NousResearch/hermes-agent). Two things it does that kow does not: a loopback management API (`POST /v1/reload`) that hot-swaps the ruleset in place, and matching on **query parameters**, which reaches APIs whose credential rides in the URL as `?key=<token>`. (Arbitrary header names are not a difference: kow's `header:` field takes any name, so vendor-specific headers like `x-api-key` and `x-goog-api-key` are ordinary `type: header` bindings.) The trade-offs run the other way on sourcing and on injector depth. Credentials are read from the proxy daemon's own process environment by default, and its Bitwarden mode refetches per daemon *restart* rather than per request, where kow sources from BWS just-in-time and never holds a static copy. Substitution is also static, so the network-exchange and request-signing injectors - `oauth2_refresh`, `oauth2_client_credentials`, `github_app`, `sigv4`, `hmac`, `jwt_bearer`, `gcp_service_account` - have no counterpart; SigV4 and SDK-minted OAuth credentials are out of scope by design and warned about rather than swapped. Reach for iron-proxy when what you want is a Go binary with a reload API in front of a container sandbox. kow stays the vault-sourced layer for credentials that need a live exchange or a signature rather than a string replacement.

Adjacent approaches (complementary, not substitution proxies):

- **[Fly.io Macaroons](https://github.com/superfly/macaroon)** ([design notes](https://fly.io/blog/operationalizing-macaroons/)): rather than hide a bearer secret behind a proxy, issue a *non-exfiltratable, attenuable* capability token, HMAC-chained caveats that can only narrow, never widen. Complementary to kow: where an upstream speaks macaroon-style tokens, a stolen token is already scoped down; kow protects the many upstreams that only accept a plain bearer / API key.

- **[Dagger secrets](https://dagger.io)**: a CI/pipeline engine with a first-class secret type that keeps values out of the build's reach and logs. Scoped to Dagger pipelines, not general agent egress: the right tool when your agent *is* a Dagger pipeline, orthogonal otherwise.

- **[AWS IAM VPC/IP conditions](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html)**: not a proxy: a defense-in-depth complement. Bind a credential's validity to a source VPC or IP (`aws:SourceVpc` / `aws:SourceIp`) so an exfiltrated key is worthless off-network. Pairs cleanly with kow: kow stops the key from leaving the process; IAM conditions make a leaked key inert.

- **OneCLI**: the same substitution-on-the-wire idea delivered as a product - a Rust MITM gateway plus a Next.js dashboard, with per-agent identities, a policy/approval layer, and one-command Docker onboarding. It ships its own encrypted secret store (Postgres, AES-256-GCM) by default and can also pull from 1Password or Bitwarden on demand; open-core (Apache-2.0 core, with proprietary enterprise/cloud tiers for org-scope policy, budgets, granular access and KMS-backed crypto). On a blocked destination it returns an explicit gateway error, where kow forwards the placeholder verbatim so the proxy never signals which destinations are bound. It is the fuller-featured choice when you want a web dashboard, team mode, and an included store; kow stays the thin single-host layer that sources from your existing vault just-in-time and never becomes a second place secrets live.

`keys-on-the-wire` is a thin substitution layer that terminates TLS for the local agent, fetches secrets from BWS just-in-time, and substitutes them on the upstream socket. It is not a vault, key manager or a rotation system: it's the missing piece between the existing vault and an autonomous agent.
